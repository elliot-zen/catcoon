# Write Spec

## 目标

产出完整、一致且可实施的 PRODUCT 与 TECH。新 Agent 只阅读项目和这两份文档，就应能理解产品行为、关键设计、实现方式与验证要求，无需依赖历史对话或自行猜测。

下文使用 PRODUCT 和 TECH 表示两类文档；实际文件名固定为小写 `product.md` 和 `tech.md`。

## Spec 目录结构

```text
specs/
├── spec.md                       # Spec 索引
├── common/                       # 跨业务共享 Spec
│   └── <issue-id>/
│       ├── product.md
│       └── tech.md
└── <issue-id>/                   # 单一业务 Spec
    ├── product.md
    └── tech.md
```

目录规则：

- `specs/spec.md` 是 Spec 索引；每个 Spec 必须在其中登记，并链接到对应的 `product.md` 和 `tech.md`。
- 单一业务能力放在 `specs/<issue-id>/`；跨业务共享能力放在 `specs/common/<issue-id>/`。
- 一个 `<issue-id>` 目录表示一个完整 Spec，必须同时包含 `product.md` 和 `tech.md`，不得将两者拆到不同目录。
- `<issue-id>` 使用与产生该需求的 Issue 对应的稳定标识（如 `123` 或 `ISSUE-123`），也可以是表达业务能力的 feature 名称（kebab-case，如 `multi-agent-issue`）；同一 Issue 或 Feature 的规格不得拆到多个目录，也不得使用与 Issue 无关的临时名称。
- 不得在 `specs/`、`specs/common/` 或其他位置创建同一能力的平行 Spec。

## 流程

### 1. 根据 Spec 索引定位

先读取 `specs/spec.md`，再按业务能力定位文档：

- 找到对应 Spec：直接更新索引指向的 PRODUCT 和 TECH，不创建同主题的第二份 Spec。
- 没有对应 Spec：创建 PRODUCT 和 TECH，并在同一次变更中加入 Spec 索引。
- 索引与实际文件不一致：先确认唯一事实源并修正索引或路径，不能让多个位置同时定义同一能力。

开始写作前，读取与需求相关的现有 Spec、设计文档、代码、配置、接口定义和测试。只采用有依据的当前事实；无法确认的内容标记为 Unknown，不自行补全。

用户提供完整产品草案或现有规格时，先逐项整理必须保留的规则、关键计算、时序、示例和边界行为。写作可以精简表达，但须逐项核对原稿与 PRODUCT、TECH 和测试的覆盖关系；新增或改变用户可观察的规则要有项目事实或用户决定作为依据。

仅产出规格、暂不实现时，先核对项目的文档状态与事实源约定，明确区分目标设计和已经上线的行为。若正式索引同时承担当前实现的事实源，应按项目约定标识未实现状态或使用设计阶段位置，避免把尚不存在的表和接口描述为已上线；实现后再同步状态。

### 2. 判断是否为公共模块

判断该模块是否属于跨业务共享能力：

- 被两个或更多业务模块共同使用；或
- 属于适用于全项目或大多数业务的公共能力。

满足任一条件时，将完整 Spec 放到或移动到 `specs/common/<issue-id>/`。同时更新 Spec 索引和所有旧引用，并删除原业务目录中的重复定义。

不满足时保留在对应业务目录，不为可能的未来复用提前抽象。业务模块使用公共能力时只引用公共 Spec；存在业务例外时，仅在业务 Spec 中描述差异。

### 3. 编写 PRODUCT 和 TECH

先写 PRODUCT，再写 TECH。PRODUCT 只描述调用方、用户或其他系统能够观察到的能力和行为；TECH 描述实现这些行为所需的技术设计。

#### PRODUCT

PRODUCT 至少包含以下部分：

1. **概述**
   - 简单描述需求解决的问题、使用者、触发场景和提供的能力。

2. **流程图**
   - 描述业务流转或状态转换。
   - 仅在确有流程或状态变化时添加；当图表比文字更清楚时使用 Mermaid。
   - 流程图必须与后文行为一致，不能用图代替关键规则、失败语义或边界说明。

3. **Happy Path**
   - 给出一条从用户、调用方或外部系统发起，到结果可见为止的完整成功流程。
   - 写清触发、必要校验、关键顺序、数据变化、外部副作用和最终结果。

4. **设计解释**
   - 按功能点详细描述能力如何工作，使读者能从中找到关键设计，而不是只看到需求目标。
   - 每个功能点说明参与者、触发条件、输入输出、校验、主要行为、状态变化、数据或外部副作用、成功结果和错误语义中的适用项。
   - 对影响行为的关键机制必须解释清楚。例如：定时任务添加后如何被调度服务发现、变更何时生效。
   - 纯代码组织和内部实现放入 TECH；但实现机制产生的可观察行为仍需写入 PRODUCT。

5. **边界情况**
   - 周全描述适用的失败、无数据、非法输入、权限不足、重复请求、并发、超时、部分成功、依赖异常、重启、恢复和兼容行为。
   - 每个边界情况写清触发条件、预期结果、已产生的数据或副作用如何处理，以及是否允许重试。
   - 对持久化或异步能力明确重启后的恢复行为。例如：服务重启后定时任务如何恢复。

6. **非目标**
   - 明确本次不提供、不改变或不负责的能力，防止实现范围自行扩张。

#### TECH

TECH 至少包含以下部分：

1. **代码组织**
   - 从代码可读性和逻辑清晰出发设计目录、模块与职责边界。
   - 写清新增或修改的代码位置、各模块负责什么、依赖方向，以及明确不属于该模块的职责。

2. **已有设计**
   - 引用继续复用或需要修改的现有设计的具体位置。
   - 位置至少精确到仓库文件及章节、代码路径及符号，不能只写宽泛的模块名称。
   - 对每项说明如何复用、需要修改什么，以及与本设计的职责边界。
   - 复用现有模块时，按需求检查其创建、查询与权限、取消、重试、结果未知、重启恢复、依赖删除和旧接口可见范围；写清本设计引入的例外及兼容边界。

3. **实现逻辑**
   - 与 PRODUCT 的功能点一一对应，逐项详细描述技术实现。
   - 按适用情况写清入口与调用链、组件协作、处理顺序、数据模型、Source of Truth、存储、协议、外部依赖、原子边界、一致性、并发、幂等、Retry、Timeout、失败处理、重启恢复、可观测性、性能和兼容约束。
   - 若涉及数据库表变动，明确新增、修改或删除的表及字段、类型、约束、索引和关联关系，并说明适用的数据迁移、回填和兼容处理。
   - 若涉及接口变动，明确新增、修改或删除的接口，以及受影响的调用方、路径与方法（或对应协议标识）、请求与响应字段的类型、必填性、范围和精度、HTTP 状态与稳定业务码、成功和失败载荷，并说明兼容处理。
   - 对每个列表、详情、权限判定和重试操作，反查所需的持久化标识、关联、索引和读取路径；对关键关系字段说明由谁写入、如何查询，以及依赖对象失效后的处理。
   - 对有状态或异步操作，按适用情况核对同键并发、终态后同键重试、同键不同请求、不同键竞争、空接收者、外部结果未知、依赖失效和重启；明确每种情形的状态、数据变化与重试边界。
   - 说明为何这些实现足以满足 PRODUCT 行为，但不记录方案讨论过程、开发任务清单或逐行编码步骤。

4. **测试**
   - 列出需要验证的测试用例。
   - 每个用例写清测试层级、场景、关键输入或前置条件、预期结果，以及需要验证的数据变化或外部副作用。
   - 覆盖 Happy Path，以及 PRODUCT 中适用的失败、边界、并发、重试、超时、重启和恢复行为。

### 4. 复核 PRODUCT 和 TECH

写完后重新读取两份完整文档，不依赖写作时的记忆进行复核：

- PRODUCT 的每个功能点、流程节点和边界行为，在 TECH 中都有实现归宿。
- 用户原稿中的规则、关键算法与边界行为均已保留，改动和新增的用户可见决定有依据；不得以概述或摘要代替核心机制。
- TECH 的每项关键实现都能追溯到 PRODUCT 行为或明确的内部必要性，没有擅自增加产品范围。
- 每个承诺的查询、通知和重试都有可定位的数据关系与接口契约；相关的共享模块、架构、数据模型及接口内容所有者已经同步或明确区分设计与当前实现。
- 流程图、Happy Path、设计解释与实现顺序一致。
- PRODUCT 的边界情况均有实现处理方式和对应测试；TECH 提出的失败与恢复机制也有产品语义或测试依据。
- 代码组织清晰，已有设计引用可定位，引用路径有效。
- Spec 与现有代码、配置、接口和测试不存在未解释冲突。
- 删除历史对话和计划后，新的 Agent 仍能据此实现并验证语义等价的功能。

发现缺失、矛盾或仍需猜测的关键规则时，返回对应章节补齐后重新复核；问题未解决前不得交付。

## 硬性约束

- PRODUCT 与 TECH 只描述当前设计，不写需求讨论、方案比较、任务进度、TODO、Debug 过程或已失效规则。
- 不虚构状态、流程、边界或实现；不适用的内容简要说明“不适用”，不为填满章节而编造。
- 所有影响行为、数据、副作用、权限、一致性、恢复或兼容性的事实必须被保留。
- 同一事实只在一个位置完整定义，其他位置通过链接引用；PRODUCT 的外部语义与 TECH 的内部实现不视为重复。
